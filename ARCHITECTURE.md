# ARCHITECTURE.md — Malik Hardware Mart

**Any agent (Antigravity or otherwise) working in this repo must follow every rule in this
file.** It is the single consolidated source for how the system is built. If a task seems to
require deviating from something here, stop and flag it as a decision — don't deviate
silently (see `AGENTS.md`'s "Think Before Coding" rule).

---

## 1. Fixed stack — do not substitute without asking

- **Framework:** Next.js 16, App Router, TypeScript, React 19 — unified repo, frontend and
  API routes together, no separate backend service.
- **Database:** Supabase (Postgres).
- **ORM:** Prisma — chosen specifically so the connection can later point at a self-hosted
  Postgres instance on a VPS with only a connection-string change, no code rewrite.
- **Auth:** custom JWT, signed server-side, delivered in an **httpOnly** cookie. Not
  Supabase Auth.
- **Styling:** Tailwind CSS **v4** (installed by `create-next-app@latest`). Theme tokens defined as CSS custom
  properties in `app/globals.css` via `@theme { }` — no `tailwind.config.ts` in v4. See `06-design-system.md`.
- **Motion:** Framer Motion (component-level interaction) + GSAP (carousel/scroll-triggered).
  See `09-design-motion-guidelines.md` for which owns which interaction.
- **Hosting:** Vercel or Render now; self-hosted VPS planned later — this is *why* Postgres
  via Prisma was chosen over the earlier Mongo/Mongoose plan.

## 2. System diagram

```
Browser
  │  HTTPS + JWT httpOnly cookie
  ▼
Next.js App Server
  ├─ Pages (src/app/**/page.tsx) — React Server + Client Components, Tailwind-styled
  └─ API route handlers (src/app/api/**/route.ts) — every access-control check lives here
        │
        ▼
   Prisma Client ─▶ Supabase Postgres (users, products, categories, use_cases, carts,
                     orders, site_settings, blog_posts, hero_slides, promo_banners)
```

## 3. The one rule everything else depends on

**Every gate — price visibility, cart, checkout, admin actions, marquee/blog editing — is
enforced inside the API route handler, against a real, current permission check.** Never in
the UI alone, and never trusting a claim baked into a JWT without a fresh check for anything
that can change after the token was issued (e.g. `isPriceVerified` — an admin can flip this
between the time a user's cookie was issued and their next request, so re-check against the
database on each request rather than trusting a 7-day-old token claim).

This rule was violated once already in a prior build pass (a "done" report claimed
verification-gating existed when the field wasn't even in the schema) — it is now the first
thing any code review checks.

|---|:---:|:---:|:---:|
| Guest | ❌ | ❌ | ❌ |

| Admin | ✅ | ❌ (not a buyer role) | ✅ |

## 5. Data model summary (Prisma, Postgres — full field lists: `03-data-models.md`)

Core commerce: `User`, `Product`, `Category`, `UseCase` (many-to-many with Product), `Cart`,
`CartItem`, `Order`, `OrderItem`.
Content/admin-editable: `SiteSettings` (single row — marquee text), `BlogPost`, `HeroSlide`,
`PromoBanner`.
Relations are foreign keys (Postgres), not embedded documents — e.g. `Order.userId` and
`OrderItem.orderId` are real FK relations with cascade rules defined in `schema.prisma`,
not the denormalized array-of-objects shape the earlier Mongoose version used.

## 7. Non-negotiables carried over from earlier decisions

- No AI-generated or externally-fetched product images — local placeholder folder with
  fallback chain only.
- Every function/route/block gets a real comment explaining intent, not restating the code.
- No hardcoded fallback secrets (`JWT_SECRET` etc.) — missing env var should fail loudly,
  not silently default to something guessable.
- No dev-only conveniences (one-click demo logins, especially admin) reachable in a
  production build.
- Animate `transform`/`opacity` only; `prefers-reduced-motion` fallback mandatory on every
  animated component (`09-design-motion-guidelines.md`).
